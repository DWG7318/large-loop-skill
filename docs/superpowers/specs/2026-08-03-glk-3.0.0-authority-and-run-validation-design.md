# GLK 3.0.0 Authority and Run Validation Design

## Status

- Design status: Owner approved for documentation and subsequent implementation.
- Owner approval: “按这个设计进入 GLK 3.0.0 的设计文档和正式施工。”
- Design date: 2026-08-03.
- Source incident: `RUN-WL-FR-GLK-001`, documented by
  `POSTMORTEM_RUN_WL_FR_GLK_001.md` on 2026-08-03.
- Current released baseline: GLK 2.4.0 at
  `d06c1198dd3e6e50090b7934a6218b5ed9e97406`.
- This document specifies architecture and acceptance boundaries. It does not
  constitute an implementation plan or an implemented release.

## Decision Summary

GLK 2.4.0 is frozen for new formal Run use. Its tag, release, repository history,
and incident evidence remain immutable and available for audit. Existing 2.4.0
artifacts do not gain 3.0 current-validity merely by being schema-valid.

The next functional release is GLK 3.0.0. It is a breaking release because it:

- splits mixed-authority receipt files into independently issued artifacts;
- introduces versioned CELL closure and exact receipt-set consumption;
- replaces per-template validation with whole-Run package loading and validation;
- requires externally verifiable role provenance for formal Runs;
- changes bootstrap success semantics;
- adds mechanical D2, D3, Owner Acceptance, liveness, and architecture-hold gates;
- locks method invocation to one canonical repository and package identity.

A 2.4.x release may publish a formal-use freeze notice and migration diagnostics.
It must not claim to repair the authority and cross-artifact defects while retaining
the 2.4 artifact model.

## Problem Statement

GLK 2.4.0 describes strong method invariants but its executable surface validates
mostly independent file shapes and free-form references. Repository validation can
pass while a Run package still contains:

- Supervisor-produced D0, D1, D2, or D3 artifacts labeled as another role;
- empty evidence, invented consumed receipt IDs, arbitrary verdicts, or invalid
  timestamps;
- inconsistent Run IDs between a contract and an embedded binding;
- a cyclic graph accompanied by a manually asserted `acyclic: true`;
- role-binding strings that do not prove issuer identity or isolation;
- mixed-authority mutable receipt files;
- a GO marked verified after only one synthetic D0/D1 pair even when the GO has
  multiple required CELLs;
- premature D2, premature D3, or Owner Acceptance without complete lineage;
- a scaffold of sample templates reported as a complete Run;
- failed role reads reported as healthy monitoring.

These are method defects, not merely executor mistakes. Green repository tests prove
that the shipped repository is internally consistent; they do not prove that a Run
package is authoritative, complete, acyclic, or eligible to advance.

## Alternatives Considered

### Patch the 2.4.x schemas

This is insufficient as the functional repair. JSON Schema can constrain local
shape, but cannot by itself establish whole-package reference existence, exact
closure, candidate lineage, graph acyclicity, issuer provenance, or authority
separation. Adding all required fields would also make the format breaking while
preserving a misleading compatibility claim.

Permitted use: a 2.4.x freeze notice, migration scanner, or diagnostic that refuses
formal use.

### Build a complete Runtime inside GLK

This could integrate signing, Broker transport, replay prevention, checkpoints,
credential lifecycle, and conversation execution. It is rejected because it would
duplicate LCagent, make GLK operationally heavy, and recreate the bootstrap deadlock
seen in RUN-WL-FR-GLK-001.

### GLK 3.0 contracts, reference validator, and provenance adapter

This is the selected approach. GLK owns method contracts, append-only artifact
semantics, mechanical admission rules, a whole-Run loader, a reference validator,
readiness and simulation gates, and state/stop rules. LCagent or another trusted
execution environment owns runtime identity, credential custody, issuance, and
liveness evidence behind a narrow adapter.

## Non-Goals

GLK 3.0 does not:

- restore the historical seven-role architecture;
- add Grapher, Planner, Router, Debugger, Tracer, or any seventh GLK role;
- introduce a `READY` state or schedulable intermediate queue;
- introduce Chain, Stage, Level, or Barrier topology;
- become an Agent runtime, session kernel, process supervisor, or scheduler service;
- implement key custody, signer stores, signing Broker services, replay prevention,
  checkpoints, credential rotation, or trusted clock infrastructure;
- issue provenance attestations itself;
- replace LCagent or another trusted execution environment;
- replace LCCoding project lifecycle, product-definition, delivery, or centralized
  security closure;
- let an outer LCCoding task or Owner gateway become a second Run Supervisor;
- rewrite or delete historical 2.4 receipts or RUN-WL-FR-GLK-001 evidence;
- use repository tests as evidence that a formal Run passed.

## Preserved 2.4 Core

The following method identity remains normative:

- exactly six roles: Run Supervisor, Worker, Checker, GO Verifier, Run Verifier,
  and Owner;
- one fresh Run Supervisor binding for every Run;
- one Run-scoped GO-to-GO directed acyclic execution graph;
- no `READY`; a waiting-clear GO enters the maximal safe `ACTIVE_GO` set directly;
- maximum-cardinality safe activation and no arbitrary serialization;
- D0, D1, D2, and D3 as distinct evidence and verification layers;
- immediate Run Owner Acceptance after valid D3;
- LCCoding ownership of centralized security closure;
- actual-consumption dependency-edge bindings;
- confirmed causal tracing, minimal descendant invalidation, and maximal-parallel
  safe reactivation;
- append-only history and explicit current-validity.

## Trust and Authority Model

### Six-role authority

| Authority | Sole GLK role |
|---|---|
| Run contract validation, graph/CELL structure, admission, activation, holds, amendments | Run Supervisor |
| Candidate implementation and D0 | Worker |
| Independent CELL validation and D1 | Checker |
| Exact GO closure validation and D2 | GO Verifier |
| Exact Run closure, graph seams, final candidate, and D3 | Run Verifier |
| Product acceptance after valid D3 | Owner |

The Run Supervisor controls method state but owns no technical verdict. It may
transport or admit an already-issued artifact only after the validator confirms the
artifact, lineage, and provenance.

### Outer gateway boundary

LCCoding and the Owner gateway may:

- supply a frozen Run contract and method lock;
- instantiate or recover the six role bindings through the trusted runtime;
- receive formal callbacks and progress;
- decide Owner-exclusive product-definition, destructive, credential, legal, or
  external-account matters;
- choose whether an architecture hold resumes through amendment or a new Run.

They may not:

- issue or alter D0, D1, D2, or D3;
- select technical verdicts;
- mutate GO state outside append-only Run Supervisor graph events;
- control the Run through an undeclared outer supervisor;
- count implementation activity as formal CELL or GO completion.

## Common Artifact Envelope

Every formal artifact is immutable after issuance and contains or resolves all
applicable fields below:

```text
schema_version
artifact_type
artifact_id
run_id
graph_id
graph_version
go_id when applicable
cell_id when applicable
candidate_id
candidate_sha256
issuer_binding_ref
execution_context_ref
evidence_refs (non-empty for technical and admission artifacts)
provenance_ref
issued_at (valid RFC 3339 UTC)
```

The `RUN_PACKAGE_INDEX` records the canonical SHA-256 digest of each formal artifact
and evidence object. An artifact does not self-declare its own digest.

Verdicts and outcomes use closed enums. A free-form non-empty string is never a
valid verdict. Formal timestamps reject sentinel dates, invalid formats, impossible
ordering, and excessive future skew. Formal evidence references must resolve to
indexed objects whose digests match.

`issuer_binding_ref` is a reference, not proof. Formal authority exists only when
the provenance adapter verifies that the referenced binding issued the exact
artifact digest within the expected Run/Graph/GO/CELL scope.

| Artifact | Sole issuer or controller | Consumes | Cannot contain |
|---|---|---|---|
| `RUN_CONTRACT` | LCCoding/Owner gateway authority outside GLK technical verdicts | Product and scope authority | D0-D3 verdicts |
| `GLK_METHOD_LOCK` | LCCoding/Owner gateway authority | Canonical repository, release, Skill, schema, validator, and adapter identities | Technical verdicts or Run health |
| `PROVENANCE_ADAPTER_PROFILE` | Trusted execution environment, selected by LCCoding/Owner gateway | Adapter contract and external trust-root references | GLK technical verdicts or graph state |
| `ROLE_BINDING` | Trusted runtime registration, verified by adapter | Run scope and capability profile | Technical verdicts |
| `GRAPH_BASELINE` | Run Supervisor | Frozen Run contract and GO contracts | D0-D3 verdicts |
| `CELL_MANIFEST` | Run Supervisor | Frozen GO contract | D0-D3 verdicts |
| `CELL_MANIFEST_AMENDMENT` | Run Supervisor | Prior manifest hash and authority evidence | Technical verdicts |
| `GO_CANDIDATE_CLOSURE` | Assigned GO Worker | Current CELL manifest and exact current D0/D1 PASS set | Checker or Verifier verdicts |
| `D0_RECEIPT` | Worker | Current CELL manifest, CELL contract, and immutable candidate | Checker or Verifier verdicts |
| `D1_RECEIPT` | Checker | Current CELL manifest, exact D0 digest, and same CELL candidate | Worker implementation or D2 |
| `SUPERVISOR_ADMISSION` | Run Supervisor | Validated artifact digest and validator report | D0-D3 technical verdicts |
| `PREFLIGHT_ADMISSION` | Run Supervisor | Derived preflight, validation, and simulation report digests | Technical verdicts or provenance claims |
| `RUN_PACKAGE_INDEX` | Run Supervisor | Prior index digest, complete formal artifact inventory, and current ledger heads | Technical validity or verdict claims |
| `D2_RECEIPT` | GO Verifier | Exact current GO candidate closure | Successor release or graph mutation |
| `GRAPH_EVENT` | Run Supervisor | Admitted D2, formal resolution, hold, or amendment | D0-D3 technical verdicts |
| `MONITOR_CONTROL` | Run Supervisor | Prior monitor record and indexed liveness attestations | Technical verdicts or `LIVE` inferred from read failure |
| `D3_RECEIPT` | Run Verifier | Exact current GO closure, D2 digest set, graph seams, final candidate | Owner verdict |
| `OWNER_ACCEPTANCE` | Owner | Valid admitted D3 and bounded Run package | D0-D3 technical verdicts |
| `SECURITY_HANDOFF` | Run Supervisor control artifact after Owner acceptance | Accepted candidate and scope | Centralized security verdict |
| Provenance/liveness attestation | Trusted external adapter | Exact adapter request, binding, scope, digest, and observation | GLK technical, graph, or Owner verdicts |

The legacy combined `CELL_RECEIPT` and `GO_RECEIPT` formats are not formal 3.0
artifacts. D0 and D1 never share a mutable record. D2 and successor release never
share a record.

`VALIDATION_REPORT`, `PREFLIGHT_REPORT`, `SIMULATION_REPORT`, and
`PROGRESS_PROJECTION` are deterministic, derived, non-authoritative outputs. They
have no GLK issuer authority, cannot advance Run state, and cannot supply a technical
verdict or provenance claim. A formal transition requires a separately issued
Supervisor admission or graph event that references the derived report digest and
inputs; `validate_run` recomputes the report rather than trusting it.

## Technical Receipt Contracts

### D0_RECEIPT

D0 is issued only by the assigned Worker. It binds:

- the current `CELL_MANIFEST` version and closure hash;
- the exact CELL contract digest;
- the CELL candidate ID and hash;
- the Worker binding and execution context;
- the allowed D0 outcome;
- non-empty implementation evidence;
- the dispatch/admission lineage required by the Run contract.

The Run Supervisor cannot issue, hold an issuance capability for, or invoke D0.

### D1_RECEIPT

D1 is issued only by the assigned Checker. It binds:

- the current `CELL_MANIFEST` version and closure hash;
- the exact D0 artifact digest;
- the same CELL contract and CELL candidate ID/hash;
- the Checker binding and clean execution context;
- a closed D1 verdict;
- non-empty independent validation evidence.

The provenance adapter must establish Worker/Checker isolation for the dimensions
required by the Run contract. A different context string alone is not proof.

### GO_CANDIDATE_CLOSURE

After every required CELL has one admitted current D1 PASS, the assigned GO Worker
issues one append-only closure. It binds the current `CELL_MANIFEST` closure hash and,
for every required CELL in deterministic order, the exact CELL candidate ID/hash,
D0 digest, and D1 digest. Canonical hashing of that set derives the new GO candidate
generation ID and GO candidate hash. D1 never consumes or binds this later closure,
so the dependency order is acyclic.

If one CELL fails D1 or changes candidate, only that CELL produces a new D0 and D1.
The other CELLs reuse their existing D1 artifacts only when manifest version, CELL
contract, CELL candidate/hash, D0/D1 evidence, provenance, expiry, and impact
current-validity are all unchanged. Reuse references the original immutable D1; it
does not copy or reissue it. The Worker then issues a new closure selecting the five
old and one new D1 in a six-CELL example. Any prior closure loses current-validity
when a selected tuple changes and cannot authorize D2.

### SUPERVISOR_ADMISSION

Admission records that the Run Supervisor mechanically accepted or rejected an
already-issued artifact. It binds:

- the admitted artifact digest;
- the exact validator version and report digest;
- the current package, graph, manifest, and candidate versions;
- the admission decision and failure codes;
- admission evidence and timestamp.

Admission cannot create, alter, reinterpret, or replace a technical verdict.

### D2_RECEIPT

D2 is issued only by the GO Verifier. It binds:

- the current GO candidate ID/hash;
- the exact `GO_CANDIDATE_CLOSURE` digest;
- the exact current `CELL_MANIFEST` version and closure hash embedded in that
  closure;
- the exact required CELL, candidate, D0, and D1 tuples embedded in that closure;
- the GO claim and acceptance contract digests;
- the GO Verifier binding and clean execution context;
- a closed D2 verdict and non-empty evidence.

D2 eligibility is mechanical; the D2 verdict is technical. The reference validator
may determine that the input closure is eligible, but only the GO Verifier may issue
the D2 artifact.

### GRAPH_EVENT

The Run Supervisor records graph effects separately after a D2 or another authorized
event is admitted. Examples include:

- successor dependency release;
- `WAITING_GO` reason removal or addition;
- maximal safe `ACTIVE_GO` recomputation;
- formal hold, resolution, amendment, invalidation, or reactivation.

A GO Verifier cannot release successors directly, and a Run Supervisor cannot turn
a graph event into a D2 verdict.

### D3_RECEIPT

D3 is issued only by the Run Verifier. It binds:

- the final Run candidate ID/hash;
- the current graph ID, version, and recomputed graph digest;
- the exact required GO set and exact admitted D2 artifact digests;
- graph-seam claims and evidence;
- the Run Feature and acceptance-claim digests;
- the Run Verifier binding and clean execution context;
- a closed D3 verdict and non-empty evidence.

The D3 eligibility engine performs only mechanical closure checks. It cannot issue a
D3 verdict.

## Versioned CELL_MANIFEST and Exact Closure

Every GO has one current versioned `CELL_MANIFEST` containing:

```text
run_id / graph_id / graph_version / go_id
manifest_version
go_contract_digest
required_cells[]:
  cell_id
  cell_contract_digest
  required
prior_manifest_sha256 when version > 1
amendment_ref when version > 1
closure_sha256
frozen_at
```

`closure_sha256` is recomputed from a canonical JSON representation of the frozen
manifest fields and deterministically ordered CELL entries.

Candidate lineage is separate from structural CELL closure. D0 and D1 bind only the
current manifest, their CELL contract, and their exact CELL candidate lineage. The
later `GO_CANDIDATE_CLOSURE` selects the complete current D0/D1 PASS set and derives
the GO candidate generation/hash. This ordering prevents D1 from depending on an
object that cannot exist until all required D1 receipts pass.

For D2 eligibility, the validator constructs the expected required CELL set from the
current manifest and requires exact equality with admitted D1 receipts:

- no missing required CELL;
- no extra CELL substituted into the closure;
- no duplicate CELL or receipt;
- every D1 binds the current CELL contract digest;
- every closure tuple selects the exact candidate/D0/D1 lineage for its CELL;
- every D1 has admitted, valid D0 lineage;
- every D1 remains current-valid under the current graph and manifest versions.

Adding, removing, replacing, or changing the required status of a CELL requires an
append-only `CELL_MANIFEST_AMENDMENT`. The amendment binds the prior manifest hash,
reason, affected claims, invalidations, new closure hash, authority, and current
graph version. A product-definition change returns to the Owner/LCCoding gateway;
it is not hidden as a mechanical amendment.

## RUN_PACKAGE_INDEX

Every formal Run root contains one canonical `RUN_PACKAGE_INDEX`. It records:

```text
run_id
index_version
prior_index_sha256 (null only for version 1)
method_lock_ref
current_graph_ref
current_cell_manifest_refs
current_candidate_refs
artifact_entries[]:
  relative_path
  artifact_type
  artifact_id
  sha256
evidence_entries[]:
  relative_path
  sha256
current_ledger_heads
index_issued_at
```

The Run Supervisor issues each index version as an immutable append-only control
artifact; it never edits an existing index in place. The loader validates the full
prior-index chain, discovers the unique unreferenced head, and rejects skipped
versions, digest breaks, branches, or multiple heads.

Index-chain files are validated separately and are not self-listed in
`artifact_entries`. The loader computes the current head digest, and the next index
or Supervisor admission binds it without creating a self-referential hash.

All formal artifacts and evidence consumed by a verdict or admission must be indexed.
Independently of the index, the loader scans the canonical formal-artifact roots and
derives the complete set required by contracts and ledger heads. That set must equal
the current index: omissions and extra unindexed formal artifacts both fail. Paths
are Run-root-relative, normalized, unique, and forbidden from escaping the Run root.
Duplicate IDs, duplicate paths, digest mismatches, and conflicting heads fail closed.

The index is an inventory, not an oracle. `validate_run` recomputes all facts that
can be derived from indexed content.

## Run Loader and validate_run

Repository validation and Run validation are separate products:

- `validate_glk` proves that the method repository, bundle, tests, and documentation
  are internally consistent.
- `validate_run` loads one complete Run package and proves its mechanical eligibility
  for a requested transition.

The Run loader does not validate files independently and then infer package health.
It first loads the complete index and referenced objects into a typed, immutable
in-memory model. It rejects ambiguity before state evaluation.

### Validation layers

1. **Serialization and schema**
   - parse canonical formats;
   - enforce closed enums, non-empty required evidence, valid hashes, and timestamps;
   - reject legacy mixed-authority artifact types in formal 3.0 mode.
2. **Package integrity**
   - verify indexed paths, file digests, unique IDs, append-only ledger links, and
     current-index uniqueness.
3. **Identity and reference integrity**
   - verify Run/Graph/GO/CELL scopes and versions;
   - resolve every consumed artifact and evidence reference;
   - reject cross-Run, cross-Graph, stale, missing, or invented references.
4. **Provenance and authority**
   - resolve every role binding through the adapter;
   - verify issuance of the exact artifact digest;
   - enforce the authority matrix and required isolation;
   - reject Supervisor provenance for D0-D3.
5. **Candidate lineage**
   - verify D0-to-D1 candidate equality;
   - verify CELL-to-GO candidate snapshot continuity;
   - verify D2-to-D3 candidate and graph-version continuity.
6. **CELL closure**
   - recompute manifest hashes and exact required CELL/D1 equality;
   - reject premature D2 and unamended CELL-set changes.
7. **GO graph integrity**
   - reconstruct nodes and edges;
   - recompute acyclicity, entry reachability, terminal coverage, edge endpoints,
     predecessor agreement, and Run Feature coverage;
   - derive entry and terminal sets rather than trusting booleans.
8. **State and admission**
   - fold admitted append-only graph events deterministically;
   - recompute waiting reasons and maximal safe activation;
   - verify amendments, invalidations, resolutions, and causal recovery;
   - reject graph-state claims unsupported by admitted events.
9. **Run closure and D3**
   - recompute the exact required GO/D2 set;
   - verify graph seams and final candidate lineage;
   - reject premature or forged D3.
10. **Owner Acceptance and handoff**
    - permit Owner Acceptance only after an admitted D3 PASS;
    - permit the security handoff only after the accepted Owner verdict.

Every validation result identifies the requested transition, package digest, validator
version, checks performed, deterministic failure codes, and evidence references.

## Provenance Adapter Boundary

GLK defines exactly four abstract adapter operations:

```text
resolve_binding(binding_ref, expected_role, expected_scope)
verify_issuance(artifact_sha256, binding_ref, expected_authority)
verify_isolation(binding_refs, required_dimensions)
check_liveness(binding_ref, deadline)
```

### resolve_binding

Returns a verifiable attestation that the binding exists, has one canonical role
type, is scoped to the specified Run/Graph/GO/CELL, and exposes the capability profile
required for validation. A declaration inside the Run package is not sufficient.

### verify_issuance

Returns a verifiable attestation that the resolved binding issued the exact artifact
digest under the expected authority. It does not accept an actor field as proof.

### verify_isolation

Returns evidence for the required isolation dimensions, including conversation,
context, mutable workspace, runtime state, evidence root, and decision inputs. A Run
contract may require additional dimensions.

### check_liveness

Returns one of `LIVE`, `STOPPED`, `UNREACHABLE`, or `UNKNOWN` with observation time,
deadline, and evidence. Read failure can never produce `LIVE`.

LCagent or another trusted execution environment implements these operations and
owns credential custody, actual issuance, replay controls, checkpoints, Broker
transport, trusted observation, and session execution. GLK consumes adapter results;
it does not implement those capabilities.

Formal Runs require a trusted adapter profile. A local demonstration adapter is
permitted only for artifacts marked `SIMULATION_ONLY`; its outputs cannot become
formal current evidence.

## Supervisor Non-Issuance Invariant

The invariant is enforced at two layers:

1. The resolved Run Supervisor capability profile excludes D0, D1, D2, and D3
   issuance operations.
2. `validate_run` rejects any technical receipt whose verified issuer role is not
   the sole role allowed by the authority matrix.

Formal preflight fails when the adapter cannot prove the capability exclusion. GLK
does not attempt to inspect or manage private keys itself.

## End-to-End Data and Permission Flow

```text
LCCoding / Owner gateway
  -> frozen RUN_CONTRACT + METHOD_LOCK + external provenance root
  -> Run Supervisor freezes GRAPH_BASELINE + CELL_MANIFESTs
  -> for each required CELL: Worker candidate + D0_RECEIPT
  -> Checker independently consumes that D0 and produces D1_RECEIPT
  -> Run Supervisor admits each current D0/D1 after validate_run
  -> after all required D1 PASS: assigned GO Worker issues GO_CANDIDATE_CLOSURE
  -> Run Supervisor admits the closure after exact-set validation
  -> GO Verifier consumes that exact closure and produces D2_RECEIPT
  -> Run Supervisor admits D2 and records GRAPH_EVENT
  -> maximal-safe WAITING_GO/ACTIVE_GO recomputation
  -> Run Verifier receives exact GO closure and produces D3_RECEIPT
  -> Run Supervisor admits D3 and opens Owner Acceptance
  -> Owner issues OWNER_ACCEPTANCE
  -> Run Supervisor emits bounded SECURITY_HANDOFF
  -> LCCoding performs centralized security closure
```

The Run Supervisor may request validation and route immutable bytes. It cannot call
a technical issuance capability on behalf of another role.

## State and Eligibility Gates

### D2 eligibility

D2 dispatch is allowed only when:

- the current `CELL_MANIFEST` validates;
- every required CELL has exactly one admitted current D1 PASS;
- every D1 has valid D0 lineage and provenance;
- one current Worker-issued `GO_CANDIDATE_CLOSURE` contains exactly those required
  CELL candidate/D0/D1 tuples and derives the GO candidate generation/hash;
- no selected tuple differs from the current-valid admitted artifact;
- no superseded closure is used;
- no relevant hold, invalidation, or unamended manifest change exists.

### D3 eligibility

D3 dispatch is allowed only when:

- every required GO is resolved by a current admitted D2 PASS or an authorized
  formal resolution that changes the required set;
- the graph is recomputed acyclic and terminal coverage is complete;
- graph seams and final candidate inputs are indexed;
- there is no active architecture, authority, provenance, or liveness hold.

### Owner Acceptance

The Owner Acceptance state machine is:

```text
OWNER_NOT_ELIGIBLE
-> OWNER_ACCEPTANCE_PENDING after admitted D3 PASS
-> LOOP_OWNER_ACCEPTED
 | LOOP_PRODUCT_REWORK
 | PRODUCT_DEFINITION_CHANGE
 | NEW_FEATURE_REQUEST
```

No Supervisor or validator default may synthesize an Owner verdict.

## Bootstrap and Readiness

`bootstrap_run` creates only a `DRAFT_SCAFFOLD`. Creating directories and sample
contracts is not a pass condition. A scaffold containing sentinel hashes, pending
verdicts, sample IDs, sample evidence paths, or epoch timestamps remains incomplete
and cannot enter formal execution.

Formal `PREFLIGHT_PASS` requires:

- a complete frozen Run contract and method lock;
- a valid Run package index and graph baseline;
- current `CELL_MANIFEST` objects for every required GO;
- complete required role bindings and trusted adapter profile;
- verified Supervisor non-issuance capability;
- required isolation dimensions;
- valid evidence roots and writable-scope separation;
- successful whole-package validation;
- successful no-side-effect simulation.

The validation, readiness, and simulation reports remain derived. Formal preflight
state changes only through a Run Supervisor `PREFLIGHT_ADMISSION` that references
their digests; `validate_run` recomputes them before accepting the admission.

Readiness is evaluated for the Run Supervisor, required Worker/Checker/GO Verifier
bindings or binding templates, Run Verifier, and Owner gateway. Missing capability
fails closed.

## No-Side-Effect Simulation

Before formal execution, one simulation-only package rehearses:

```text
D0 -> D1 -> Supervisor admission -> GO candidate closure -> admission
-> D2 -> graph event -> D3 -> Owner eligibility
```

The simulation must prove:

- correct issuer authority for every artifact;
- Supervisor inability to issue D0-D3;
- D0/D1 candidate equality and Worker/Checker isolation;
- exact multi-CELL D2 closure;
- successor release only through a Supervisor graph event;
- exact required-GO D3 closure;
- one fork with maximal-safe parallel activation;
- one liveness failure producing `UNKNOWN` or `UNREACHABLE`, never healthy;
- one architecture hold and one legal recovery decision;
- no mutation of production assets or formal Run current state.

All simulation artifacts are marked `SIMULATION_ONLY`, stored separately, and
rejected as formal evidence.

## Architecture and Authority Holds

The following immediately enter `RUN_AUTHORITY_HOLD`:

- Supervisor provenance on D0, D1, D2, or D3;
- an issuer/role/scope/candidate/digest mismatch;
- cross-Run references or broken append-only lineage;
- a cyclic graph;
- premature D2, D3, Owner Acceptance, or security handoff;
- package or ledger corruption;
- duplicate monitoring control for one Run.

One proven technical-receipt authority violation is sufficient for an immediate
hold. It is not treated as ordinary CELL rework.

Two consecutive architecture-level HIGH findings in the same control or admission
path enter `RUN_ARCHITECTURE_HOLD`. The Run may not continue accumulating local
rework. The Owner chooses one of:

- a bounded, frozen, append-only architecture amendment with revalidation; or
- sealing the Run and starting a new Run from a clean ledger.

Product-definition changes still route through the Owner/LCCoding gateway.

## Liveness, Recovery, and Monitor Deduplication

Role observation failure is fail-closed:

- a failed or timed-out read is `UNKNOWN`;
- an exceeded deadline becomes `ROLE_UNREACHABLE`;
- no technical artifact from that role is inferred, fabricated, or accepted;
- affected dispatch/admission stops while unrelated safe GO work may continue;
- recovery resumes the existing role task from an externally attested recovery
  reference or callback when the trusted runtime supports it; GLK stores only the
  reference.

GLK does not create standalone cron tasks. Every Run has at most one monitor control
chain. Each `MONITOR_CONTROL` version is append-only and binds its prior digest,
deterministic `monitor_key`, existing Supervisor task reference, callback target,
observation deadline, and indexed liveness attestation. A duplicate key, forked
monitor head, or monitor that creates another visible task is rejected and places
monitoring under hold.

Roles should send completion, blocker, and failure callbacks. Polling is a bounded
fallback, not a source of health truth.

## Formal Progress Model

Every status report includes both closure dimensions:

```text
required_go_count
d2_verified_required_go_count
required_cell_count
d1_accepted_required_cell_count
active_go_ids
waiting_go_ids with typed reasons
blocked_or_unreachable_role_bindings
current holds
current graph_version and CELL_MANIFEST versions
```

The headline form is:

```text
GO D2: <verified required GO>/<required GO>
CELL D1: <accepted required CELL>/<required CELL>
```

Commits, tests, generated evidence files, sequence numbers, and rework attempts are
secondary activity metrics and never formal progress.

## Supply-Chain and Version Canonicalization

Until an explicit Owner-approved repository migration occurs, the canonical source
is:

```text
repository: https://github.com/DWG7318/large-loop-skill
invocation: graph-loop-skill
version: 3.0.0
```

Every formal Run freezes a `GLK_METHOD_LOCK` containing:

```text
canonical_repository
commit_sha
release_tag
method_version
schema_bundle_sha256
skill_package_sha256
validator_version and digest
adapter_profile_id and contract version
```

Preflight verifies the active invocation against the lock. It rejects:

- multiple discoverable `graph-loop-skill` installations with different identities;
- the historical 2.0.0 seven-role/READY package under the same invocation;
- a repository, tag, commit, Skill, schema, validator, or adapter-contract mismatch;
- an invocation that points to a nonexistent or non-canonical repository.

The failure state is `GLK_SUPPLY_CHAIN_CONFLICT`. Formal execution cannot continue
until exactly one canonical package matches the Run lock.

## 2.4 to 3.0 Migration

### Preserve unchanged

- six-role method identity and fresh Run Supervisor principle;
- GO DAG semantics and maximal-safe WAITING/ACTIVE scheduling;
- D0-D3 layer meanings;
- immediate Owner Acceptance and LCCoding security handoff boundary;
- actual-consumption edges, causal traces, impact slicing, and reactivation;
- append-only historical evidence;
- repository hash and cross-platform validation discipline.

### Convert and revalidate

- Run contracts, GO contracts, and graph baselines;
- graph amendments, formal resolutions, causal traces, and impact projections;
- candidate and evidence indexes;
- fresh 3.0 role-binding declarations accompanied by trusted provenance.

Conversion never preserves derived trust. The 3.0 loader recomputes digests, DAG
facts, references, required sets, lineage, and current-validity.

### Historical-only

- 2.4 role-binding strings;
- 2.4 combined CELL and GO receipts;
- 2.4 D0-D3 artifacts without trusted 3.0 provenance;
- RUN-WL-FR-GLK-001 control ledger and all derived receipts;
- 2.4 bootstrap workspaces and validation reports.

These remain immutable audit evidence but cannot satisfy a 3.0 admission or closure.

### Discard from the formal 3.0 model

- combined `CELL_RECEIPT` and `GO_RECEIPT` artifact types;
- the `acyclic: true` assertion as proof;
- one `Go` object with only one D0, D1, and D2 slot;
- free receipt IDs without resolved digest references;
- free actor strings as provenance;
- per-template validation as a Run completion claim;
- bootstrap output that reports a complete Run from sample templates;
- health reports derived from failed reads;
- standalone or duplicate cron monitoring.

Discard means “not accepted as a formal 3.0 construct,” not deletion of history.

## Implementation Decomposition

The approved design can be implemented as bounded workstreams. This section defines
boundaries, not a step-by-step implementation plan.

### Contract bundle

Owns 3.0 artifact schemas, closed enums, common envelope, authority matrix,
`CELL_MANIFEST`, `GO_CANDIDATE_CLOSURE`, amendments, package index, method lock,
progress, and migration formats. It does not own runtime provenance implementation.

### Immutable package loader

Owns canonical path handling, package indexing, typed loading, digest resolution,
duplicate detection, and immutable in-memory objects. It does not decide technical
verdicts.

### Cross-artifact validation engine

Owns identity/reference integrity, candidate lineage, CELL closure, graph
recomputation, state replay, D2/D3 eligibility, Owner gating, and deterministic
failure codes.

### Provenance adapter contract and conformance harness

Owns the four abstract interfaces, response schemas, trusted-profile selection, and
simulation-only fixture behavior. LCagent owns production adapter implementation and
runtime security.

### Admission and graph event state machine

Owns Supervisor mechanical admission, WAITING/ACTIVE recomputation, holds,
amendments, exact successor release, and deterministic event folding. It cannot
issue D0-D3.

### Bootstrap, readiness, and simulation

Owns `DRAFT_SCAFFOLD`, formal preflight, sample-value rejection, six-role readiness,
non-issuance probes, and the no-side-effect end-to-end rehearsal.

### Liveness, monitoring, and progress

Owns fail-closed liveness states, existing-task callback references, deterministic
monitor deduplication, architecture holds, and dual GO/CELL progress reporting. It
does not implement a task scheduler.

### Supply chain, migration, and release conformance

Owns method locking, invocation conflict detection, 2.4 conversion diagnostics,
historical-only labeling, repository integrity, and release checks.

The loader and contract bundle are prerequisites for cross-artifact validation. The
provenance adapter contract can be implemented independently against fixed response
fixtures. Admission, preflight, liveness, and migration consume the validator rather
than reimplementing its rules.

## Acceptance Criteria

GLK 3.0.0 is acceptable only when all statements below are evidenced:

1. New formal 2.4 Runs are refused or clearly frozen; historical artifacts remain
   accessible and unchanged.
2. The six roles, no-READY DAG, maximal-safe activation, D0-D3 meanings, Owner
   Acceptance, LCCoding boundary, and causal recovery remain intact.
3. D0, D1, admission, D2, graph event, D3, and Owner Acceptance are independent
   append-only artifacts with one authority each.
4. The Run Supervisor cannot issue, hold an issuance capability for, or invoke
   D0-D3 under a trusted adapter profile.
5. Every formal artifact binds candidate lineage, role binding, context, non-empty
   evidence, scope, timestamp, and indexed digest.
6. `CELL_MANIFEST` and `GO_CANDIDATE_CLOSURE` prevent premature D2, unamended
   CELL-set drift, stale closure reuse, and unnecessary revalidation of unchanged
   current-valid CELL D1 artifacts.
7. D3 requires the exact current required GO/D2 closure and graph-seam evidence.
8. `validate_run` loads and validates the complete Run package across all ten layers.
9. Graph acyclicity and coverage are recomputed from actual nodes and edges.
10. Free role strings and actor fields cannot establish provenance or isolation.
11. Bootstrap scaffolding cannot report formal readiness; preflight and simulation
    are distinct fail-closed gates.
12. Liveness read failures cannot produce healthy status, and monitor controls cannot
    create duplicate tasks.
13. Architecture-level authority failures stop the Run rather than entering infinite
    local rework.
14. Formal progress reports both required GO/D2 and required CELL/D1 completion.
15. One method lock prevents 2.0.0, 2.4.0, and 3.0.0 identity collisions under the
    same invocation.
16. All R01-R28 regressions fail for the intended reason before implementation turns
    them green, and all positive conformance cases pass afterward.
17. The GLK repository contains no key custody, Broker, replay, checkpoint, or Agent
    runtime implementation.
18. Repository validation and Run validation report their scopes distinctly.
19. Migration never upgrades unproven 2.4 receipts into formal 3.0 current evidence.
20. Documentation, schemas, validators, templates, examples, tests, manifests, and
    release reports agree on version 3.0.0 and the canonical repository identity.
