# GLK 4.1.0 Shared Supervisor Design

## Status and decision

- Design date: 2026-10-11.
- Status: Owner-approved correction that supersedes the unreleased GLK 4.0.0 candidate.
- Scope: GLK repository and installed GLK Skill collection only.
- Version: publish as `4.1.0` with tag `v4.1.0`; 4.0.0 remains an unpublished intermediate candidate.
- Supersedes: every current or historical instruction that gives each child SLK a different Supervisor Agent.

GLK 4.1.0 has exactly one visible, stable Supervisor Agent for one GLK Run. That same Agent owns the Node DAG and binds the Supervisor role of every child SLK Run. The number of Supervisor Agents is therefore constant: one per GLK Run, independent of Node count, SLK count, Fusion, or D2 Repair.

## Problem

The first 4.0 candidate combined one GLK Supervisor with a new Supervisor for every child SLK. That N+1 arrangement duplicated control authority, made graph handoffs indirect, and created unnecessary conversations without improving child-Run isolation.

The correction removes those extra agents. It does not remove child SLK boundaries or replace SLK evidence, checks, tokens, records, workspaces, or archives.

## Considered approaches

### Selected: one Agent with run-scoped Supervisor bindings

The GLK Supervisor Agent is registered once in the GLK roster and is referenced by every child SLK Supervisor binding. Each binding has a distinct child SLK Run identity and scope tuple. This preserves ordinary SLK contracts while preventing additional Supervisor creation.

### Rejected: GLK Supervisor plus one Supervisor Agent per child SLK

This is the incorrect N+1 design. It multiplies control conversations, inserts unnecessary handoffs, and contradicts the one-Supervisor GLK control plane.

### Rejected: merge all child SLKs into one large SLK Run

This would remove the independent Checker, Worker, SLK token, central record, construction workspace, CELL loop, D0/D1/D2, and archive that make every child outcome independently reviewable.

No coordinator, broker, router role, hidden agent, or runtime service is introduced.

## Authority and identity model

One GLK Run records one shared Supervisor Agent identity and stable conversation binding. A child SLK registers a Supervisor role binding that points to that identity; registering the binding never creates another Agent or conversation.

Every shared-Supervisor action is scoped by the complete tuple:

```text
GLK_RUN_ID + NODE_ID + SLK_RUN_ID + CELL_ID
```

`CELL_ID` is the current CELL when an action is CELL-specific and the explicit non-CELL sentinel when the child action is at Run closure. The shared Supervisor reloads the addressed child central record and current SLK token before dispatch, admission, D2, routing, or archive work. It never relies on memory-only context.

A missing tuple component, a tuple that resolves to more than one child, a token/record mismatch, or a request from a Checker or Worker bound to another child SLK fails closed. The method does not guess an identity or create a replacement Supervisor.

## Child SLK independence

Every child SLK remains a complete, independent Run with its own:

- SLK Run ID and Supervisor role binding;
- Checker and Worker bindings;
- current SLK token and central record;
- isolated construction workspace and resources;
- CELL plan and D0/D1/D2 evidence;
- rework loop, communication evidence, and archive state.

Fusion and conditional D2 Repair are ordinary child SLK Runs under the same rules. Closing a child archives its child members according to SLK, but never archives the shared GLK Supervisor. The shared Supervisor remains available until the entire GLK Run is terminal.

## Graph and child data flow

1. The shared Supervisor freezes the Node DAG and the one-Agent binding.
2. It creates each child SLK Run record and binds itself as that Run's Supervisor without creating another conversation.
3. It creates or activates that child SLK's isolated Checker and Worker through current SLK rules.
4. It sends formal input only to the Checker/Worker pair belonging to the exact scope tuple.
5. The child completes its CELL loop, D0, D1, child D2, and archive evidence independently.
6. The shared Supervisor records the usable child delivery against its Node and releases successors only when all required child SLKs for that Node have closed successfully.
7. Fusion child SLKs integrate direct predecessor deliveries in isolated workspaces and complete their own D2.
8. The same shared Supervisor then performs the distinct GLK final D2. A failure activates the conditional D2 Repair child SLK Run; a repaired candidate returns to the same final D2 boundary.

Child D2 establishes one child SLK Run. GLK final D2 establishes the complete Graph. Neither substitutes for the other.

## Communication and isolation

The only control hub is the shared Supervisor. Checker and Worker channels are child-local:

```text
shared Supervisor <-> child Checker <-> child Worker
```

There is no Checker-to-Checker, Worker-to-Worker, or cross-child Checker/Worker dispatch, checking, waiting, or delivery. Graph inputs and outputs move through the shared Supervisor using immutable child delivery identities. After one routing action the Supervisor ends its turn; it does not monitor members with `wait_threads`.

## Authoritative files

- `GLK-GRAPH.md` records the Node DAG, Node-to-child-SLK membership, and interfaces.
- `GLK-ROSTER.md` records the shared Supervisor Agent once and every child SLK's independent bindings and resources.
- `GLK-RUN-<RUN-ID>.md` records append-only graph events using the complete scope tuple and references each child central record.

The roster must prove that all child Supervisor bindings resolve to the one shared Agent identity and that Checker, Worker, token, record, and workspace bindings remain distinct. A second Supervisor Agent identity is a configuration error.

## Failure handling

- Duplicate Supervisor Agent identity: reject setup and do not start construction.
- Scope collision or incomplete tuple: reject the action without routing or verdict.
- Cross-child Checker/Worker reference: reject and retain both child states.
- Child failure or block: keep that child in its own SLK recovery path and hold only affected graph descendants.
- Shared Supervisor unavailable: retain all child records and use the existing visible-conversation recovery path; never create a substitute Supervisor.

## Migration

Published releases remain immutable. Existing Runs continue under the exact version they started with. A new 4.1 Run uses the shared-Supervisor architecture from the beginning; an in-flight Run is not silently rebound.

The global GLK installation is replaced only after repository tests, manifest validation, package validation, main integration, tag, and Release all bind the same accepted commit.

## Verification strategy

Repository tests must first fail against the old N+1 text and then prove:

- exactly one Supervisor Agent identity for multiple ordinary child SLKs, Fusion, and D2 Repair;
- distinct child Run IDs, Checkers, Workers, tokens, records, and workspaces;
- complete scope tuple markers for Supervisor actions;
- child-local communication and rejection of cross-child Checker/Worker routes;
- child D2 remains distinct from GLK final D2;
- no active or historical repository instruction still prescribes one Supervisor Agent per child SLK;
- all four Skills, bilingual guidance, templates, migration, changelog, validation report, and manifest agree.

## Acceptance criteria

The correction is accepted only when:

1. one GLK Run can contain several ordinary child SLKs, Fusion, and D2 Repair while naming exactly one Supervisor Agent;
2. every child SLK remains independently identifiable, reviewable, and archivable;
3. all formal Supervisor work binds the complete four-part scope tuple;
4. a second Supervisor identity, scope collision, or cross-child member route fails closed;
5. focused and full tests, repository validation, Skill validation, package validation, and contradiction scans pass;
6. the released package and installed global GLK Skills are byte-identical to the accepted repository commit.

## Non-goals

This correction does not modify SLK, CLK, LCCoding, the Node DAG topology, child CELL logic, D0/D1/D2 meaning, model selection, Agent runtime, session transport, credentials, or deployment infrastructure.
