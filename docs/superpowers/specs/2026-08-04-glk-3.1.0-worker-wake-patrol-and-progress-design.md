# GLK 3.1.0 Worker Wake, Run Patrol, Layered Progress, and CELL Capacity Design

## Status

- Status: Owner approved for direct design, plan, and TDD implementation.
- Design date: 2026-08-04.
- Target version: 3.1.0.
- Base: accepted GLK 3.0.0 commit `bbd540311cb231472ef1a132ef5d174e5623afa0`.
- Scope: GLK only.
- Compatibility: additive control-plane contract change with versioned migration; the six technical roles and D0-D3 authority model remain unchanged.
- Owner hard rules: Worker-only wake escalation, bounded Supervisor waiting, one Run patrol, precise subtask/subagent classification, layered realtime progress, device/cumulative-load-aware CELL capacity planning, and Owner-only thread pin authority.

This document is the normative design for GLK 3.1.0. The accepted GLK 3.0.0 authority and Run-validation design remains normative wherever this document does not explicitly amend it.

## Problem Statement

GLK 3.0.0 validates technical authority and Run closure, but it does not completely specify how a finished Worker wakes its original Checker when direct messaging fails. It also leaves room for a Supervisor to remain online by waiting for members, provides no uniquely constrained Run patrol, and does not mechanically distinguish visible peer tasks from prohibited hidden subagents.

Progress vocabulary is also incomplete. A Worker delivery, a Checker D1 acceptance, a GO candidate, a D2 verdict, a D3 verdict, and Owner Acceptance are different facts. Treating them as one generic completion percentage makes rework and amendments misleading.

Finally, CELL planning can underestimate late-project work. Small code changes may require large regression, evidence, hashing, integration, context-recovery, and independent-check costs. When device facts and cumulative engineering load are ignored, an oversized CELL is discovered only after dispatch and must be split repeatedly. This is a planning defect, not ordinary product failure.

GLK 3.1.0 closes these operational control gaps without becoming an Agent Runtime, scheduler, generic device monitor, or messaging bus.

## Preserved GLK 3.0 Core

The following remain unchanged:

- exactly six formal roles: Run Supervisor, Worker, Checker, GO Verifier, Run Verifier, and Owner;
- one fresh Run Supervisor per Run;
- GO-to-GO DAG inside one Run;
- no `READY` state;
- `WAITING_GO` moves directly to a maximal safe `ACTIVE_GO` set;
- independent append-only D0, D1, admission, D2, graph-event, D3, and Owner Acceptance artifacts;
- versioned `CELL_MANIFEST`, exact GO candidate closure, and current-valid D1 reuse rules;
- ten-layer `validate_run`, abstract four-operation provenance adapter, and fail-closed authority holds;
- actual-consumption causal tracing and minimal-impact recovery;
- LCCoding ownership of outer lifecycle and centralized security routing;
- LCagent or another trusted environment ownership of sessions, credentials, issuance transport, Broker, replay, checkpoints, and Runtime provenance.

The Run patrol is not a seventh role. Wake, patrol, progress, and capacity artifacts do not issue or replace D0-D3 verdicts.

## Non-Goals

GLK 3.1.0 does not:

- add a generic inter-role message bus;
- extend the Worker wake ladder to Checker, Verifier, Supervisor, Owner, Router, or Grapher communication;
- restore a seventh technical role or `READY`;
- create replacement Workers or Checkers;
- create hidden, background, or delegated Agents;
- implement thread, heartbeat, timer, process, device, or session Runtime services;
- introduce a continuous device telemetry collector;
- let the patrol inspect code quality, plans, product correctness, or verification sufficiency;
- let the patrol repair, take over, re-plan, or re-dispatch work;
- let capacity shortage masquerade as a dependency edge;
- change one GO outcome into multiple GO outcomes merely to split a CELL;
- weaken D0-D3 evidence or acceptance requirements after a split;
- introduce a single completion percentage.
- let any method role pin or unpin a Codex task.

## Alternatives Considered

### Embed wake, patrol, progress, and capacity in one Supervisor controller

Rejected. It would make the Supervisor a long-running Runtime, concentrate unrelated state, and encourage wait loops. It would also blur Worker-owned delivery, Checker-owned D1 acceptance, patrol observations, and Supervisor planning authority.

### Use a generic Agent messaging and monitoring service inside GLK

Rejected. A generic service would duplicate LCagent responsibilities, expand the mechanism to all roles, and make prohibited subagent creation difficult to distinguish from visible peer tasks.

### Add four narrow method contracts and reuse existing validation

Selected. GLK adds a Worker-only wake protocol, a non-authoritative Run patrol contract, derived layered progress projections, and Supervisor-owned capacity control artifacts. Trusted thread, heartbeat, clock, device-observation, and issuance operations remain adapter-provided external capabilities.

## Architecture Overview

GLK 3.1.0 adds four narrow modules:

1. `worker_wake`: validates frozen Worker/Checker bindings, executes the four-level escalation through an injected gateway and clock, and emits immutable operational records.
2. `run_patrol`: validates exactly one patrol conversation and heartbeat, derives fixed mechanical patrol observations, and validates terminal closure order.
3. `progress_reporting`: derives role-specific messages and counts from current validated receipts, verdicts, manifests, graph versions, and plan versions.
4. `cell_capacity`: validates versioned device facts and cumulative load, evaluates a pre-dispatch capacity gate, records scope excess and post-dispatch split defects, and contributes resource conflicts to maximal-safe GO activation.

`preflight`, `simulation`, `run_control`, schemas, templates, and repository validation integrate these modules. None of the modules performs network access, creates tasks, schedules heartbeats, reads devices directly, or stores credentials.

## Worker-Only Wake Protocol

### Frozen wake scope

Before dispatch, the control plane freezes an immutable `WORKER_CHECKER_WAKE_BINDING` containing:

- contract version;
- Run, GO, CELL, and Round identifiers;
- Worker binding identifier, thread identifier, and host identifier;
- original Checker binding identifier, thread identifier, and host identifier;
- current `CELL_MANIFEST` identifier/version and Required CELL count;
- CELL ordinal in that manifest;
- expected ACK scope;
- allowed operational capability profile digest;
- freeze time and digest.

The Checker identity may be re-resolved only from this frozen role registry. A missing task, host mismatch, or invalid registry cannot authorize guessing an identifier or creating a replacement Checker.

### Scoped Worker message

The runtime Worker-to-Checker completion receipt `完成，请检验` is replaced by a deterministic scoped short message:

`GO <GO_ID> CELL <ordinal>/<required_cell_count> 已交付，请检查`

`BLOCKED` and `EXECUTION_FAILURE` use the same Run/GO/CELL/Round identity and ordinal, with the disposition stated explicitly. The ordinal is the current position in the versioned Required CELL set. It is not an accepted count. Rework of the same CELL keeps the same ordinal.

This replacement applies only to method-runtime Worker wake messages. A method-maintenance task may still return the exact cross-task completion phrase required by its supervising task.

### Checker ACK

The original Checker must first emit:

`WAKE_ACK RUN=<run_id> GO=<go_id> CELL=<cell_id> ROUND=<round_id>`

An ACK is valid only when every scope field and the Checker binding match the frozen wake binding. Mechanically verified evidence that this exact Checker has started processing the same scope is equivalent to a matching ACK. Free text, another Checker, another Round, or another host does not stop escalation.

After ACK, the Checker displays:

`收到<GO_ID> CELL <ordinal>/<required_cell_count>，开始检查`

### Four fixed escalation levels

Each level has a maximum two-minute ACK window. Tests use an injected clock and never sleep in real time.

1. At T+0, send the scoped message to the frozen Checker thread and host. Wait at most two minutes for matching ACK or verified processing evidence.
2. At T+2, read/list the original task, validate existence, host, archive state, and running evidence. It may unarchive that same task and re-resolve the same Checker from the frozen registry, then resend. It may not guess an ID or create a substitute. Wait at most two minutes.
3. At T+4, create or update one deterministic, temporary, unique Checker wake heartbeat. It does not create a conversation. The Checker ACKs first and immediately deletes the temporary heartbeat. Wait at most two minutes.
4. At T+6, append one fixed `PENDING_WAKE` record containing Worker, Checker, Run, GO, CELL, Round, all three attempts, errors, and times. The Worker may send a best-effort notification, but the unique patrol must discover it from its own heartbeat even if every message failed.

### Stop and deduplication rules

On a valid ACK or verified start:

- no later level may run;
- the temporary heartbeat is deleted if present;
- a matching `PENDING_WAKE` is consumed/closed if present;
- the same scope cannot trigger duplicate work, duplicate verification, or a second Worker/Checker;
- a replayed ACK is idempotent and cannot alter accepted progress.

Wake identity is `(run_id, go_id, cell_id, round_id, worker_binding_id, checker_binding_id)`. Heartbeat and pending keys are deterministic hashes of that identity.

### Worker capability preflight

Before dispatch, the Worker operational capability profile must prove all of:

- `send_message_to_thread`;
- `read_thread`;
- `list_threads`;
- `unarchive_thread`;
- bounded wait for `WAKE_ACK`;
- create/update and delete a temporary heartbeat;
- append `PENDING_WAKE`.

Capabilities are attested through the existing provenance/profile boundary and bound to the exact Worker, Run, workspace/context isolation, and method lock. Missing, free-text-only, untrusted, or mismatched capabilities fail closed before dispatch. These operations do not grant D0-D3 authority.

Other roles attempting to invoke this ladder are rejected as `WAKE_ROLE_FORBIDDEN` before any gateway operation.

## Supervisor Waiting Rule

The Run Supervisor must end its turn after dispatch or control work. It may use `read_thread` or a `wait_threads` snapshot with `timeoutMs: 0`. It may not:

- use positive-duration `wait_threads` to stay online;
- place `wait_threads` inside a loop;
- wait for all Workers;
- call the Worker wake ladder.

Only the Worker wake ladder may perform a bounded ACK wait, and each level is capped at two minutes by the injected clock contract. The patrol treats proven Supervisor waiting as a control alert, not as a technical verdict.

## One Run Patrol

### Binding and uniqueness

Each Run has exactly one visible `RUN_PATROL_CONVERSATION` and exactly one patrol heartbeat. A versioned `MONITOR_CONTROL` binds:

- Run identifier and current index head;
- patrol conversation thread and host identifiers;
- patrol heartbeat identifier;
- deterministic patrol key;
- model `gpt-5.6-luna` and reasoning effort `xhigh`;
- frozen project difficulty `HIGH`, `MEDIUM`, or `LOW`;
- corresponding interval 10, 15, or 30 minutes;
- existing callback/reference roots;
- prior control digest and current head.

`MONITOR_CONTROL` no longer binds the Supervisor task as the liveness monitor. Duplicate patrol conversations, duplicate heartbeat IDs, chain forks, or a second visible patrol fail closed. GLK validates descriptors and observations; an external trusted environment owns actual conversation and heartbeat operations.

### Patrol authority boundary

The patrol is non-authoritative, non-technical, and non-product-working. It cannot issue D0-D3, admissions, graph events, Owner Acceptance, capacity gates, or product judgments. It cannot repair, take over, re-plan, re-dispatch, or accept work.

It is forbidden from invoking `create_thread`, `fork_thread`, `spawn_agent`, or `delegate_task`. Those capabilities must be absent from its profile.

### Mechanical checks

At each heartbeat, the patrol checks only:

- the Loop has stopped without a valid pause, `BLOCKED`, terminal state, or external-wait reason;
- a `PENDING_WAKE` remains unprocessed;
- evidence shows `spawn_agent`, `delegate_task`, a hidden Agent, or a background Agent;
- the Supervisor is using a positive-duration or looping `wait_threads` operation;
- more than one patrol conversation or patrol heartbeat exists;
- terminal Loop state exists but the patrol remains open.
- a Run-related task is pinned by an Agent/method operation, or its pin provenance cannot be proved.

Normal work, a formal pause, legal `BLOCKED`, and a bound external condition are not errors. Patrol output is a fixed status, evidence-reference list, and alert-code list. It does not report engineering progress.

### Pending wake handling

The patrol reads indexed operational pending-wake records using its own heartbeat. It may wake the already frozen Checker through the declared callback route and append a non-authoritative consumption observation. It may not choose a different Checker, create a task, or perform the check itself.

### Terminal closure

After the method has formally terminated, the only valid sequence is:

1. observe and bind `LOOP_TERMINAL`;
2. delete the patrol heartbeat;
3. append `PATROL_CLOSED`;
4. archive the patrol conversation.

Closing early, leaving the heartbeat after closure, or leaving the conversation unarchived is rejected.

## Subtask and Subagent Classification

The following are method work units, not subagents:

- GO, CELL, Round, plan step, and text containing `子任务`;
- a visible task with a stable thread ID in the same project sidebar;
- the unique visible Run patrol conversation.

The following are subagent evidence and are forbidden in this GLK configuration:

- `spawn_agent`;
- `delegate_task`;
- a hidden Agent;
- a background Agent.

Classification is based on closed event/capability types, not keyword substring matching. Therefore a visible task or the word `子任务` cannot trigger a false alert, while an actual `spawn_agent` event fails closed. Readiness, simulation, schemas, validators, and negative tests use the same closed classifier.

## Owner-Only Thread Pin Authority

Creating a role task, dispatching work, entering `ACTIVE_GO`, waiting for a receipt, blocking, reworking, verifying, reaching a milestone, or project importance never authorizes Pin. Every method role, including the six formal roles, any legacy Router/Grapher label, and the patrol, is permanently forbidden from calling `set_thread_pinned(true)` or an equivalent Pin operation.

The only legal Pin sources are:

- an Owner's explicit manual choice in the Codex UI; or
- an Owner's explicit item-specific authorization in the current Run.

The method may not infer authorization from frequent Owner viewing, a Supervisor label, a long-lived role, or task importance. Pin and task archive/unarchive/lifecycle controls are independent. Pin cannot replace status, progress, role binding, or recovery indexing.

For every pinned Run-related task, the patrol consumes available closed operation/provenance evidence:

- proven Owner manual or explicitly authorized Pin is legal and does not alert;
- any Agent/method Pin call records `UNAUTHORIZED_THREAD_PIN` even if a later Unpin occurred;
- unproved Pin origin records `PIN_PROVENANCE_UNKNOWN` and asks the Owner to inspect it.

The patrol reports only. It never unpins a task because an unknown Pin could be an Owner's manual choice. No method role needs or receives Pin capability. Readiness fails if any role/patrol capability profile grants it. Simulation verifies creation and dispatch cause no Pin calls.

## Layered Realtime Progress

### Progress facts and states

The closed progress-state vocabulary is:

- `DELIVERED`;
- `D1_ACCEPTED`;
- `GO_CANDIDATE_READY`;
- `D2_VERIFIED`;
- `RUN_VERIFIED`;
- `OWNER_ACCEPTED`.

These states are not interchangeable and must not be summarized as generic completion.

### Worker to Checker

The Worker reports only the scoped current CELL delivery, `BLOCKED`, or `EXECUTION_FAILURE`. Delivery does not increase an accepted count. All four wake levels reuse the exact same progress identity and message digest.

### Checker local progress

The Checker is the finest progress layer. Its projection is derived from current-valid D1 receipts for the current manifest:

- PASS: `GO-X CELL验收 a/N，下一CELL或GO候选状态`;
- FAIL/REWORK: `GO-X CELL验收仍为 a/N，当前CELL进入Rxx返工`;
- BLOCKED: retain `a/N` and show the bound blocker.

Only the first current-valid D1 PASS for a Required CELL increases `accepted_cell_count`. Delivery, green tests, check start, rework rounds, duplicate receipts, stale generations, and free text never increase it.

### Checker to Supervisor

The Checker sends no per-CELL stream to the Supervisor. When every Required CELL in the current manifest has a current-valid D1 PASS and the current GO candidate closure exists, it emits one deduplicated GO-boundary milestone:

`GO <go_ordinal>/<required_go_count>；本GO CELL <N>/<N>已验收；当前状态=GO_CANDIDATE_READY`

Subsequent status may be `VERIFYING` or `D2_VERIFIED`, but candidate readiness alone is never described as GO verified or complete. The milestone binds graph version, manifest version, GO candidate generation, and digest.

### Supervisor to Owner-visible progress

The Supervisor emits one concise global projection only when a GO, outer Level reference, Graph, Run, hold, or Required-set version changes materially. It does not relay every Worker/Checker message.

The projection contains:

- current plan/load/capacity profile versions;
- `d1_accepted_required_cell_count / required_cell_count` from current D1 receipts and manifests;
- `d2_verified_required_go_count / required_go_count` from current D2 receipts and graph;
- active GO IDs;
- waiting GO reasons;
- current holds;
- graph version and per-GO manifest/plan versions;
- Run state, distinguishing D3 Run verification from Owner Acceptance.

It may display an outer LCCoding Level identifier as a bound reference but does not create Level topology or barrier semantics. It never emits a single percentage.

### Other roles

GO Verifier and Run Verifier emit only formal verdicts. The patrol emits only operational status/evidence/alerts. Owner Acceptance remains a formal decision. No Router, Grapher, or other label duplicates Checker or Supervisor progress.

### Amendments and denominator changes

Numerators come only from current-valid receipts or verdicts. Denominators come only from current versioned Required sets. A graph, manifest, or CELL-plan amendment creates a new version and recomputes current denominators. Historical projections remain immutable but are not displayed as current truth. A CELL split does not itself increase accepted progress.

## Device and Cumulative Engineering Load Contracts

### DEVICE_CAPACITY_PROFILE

Before Run/plan freeze, the Supervisor records a versioned append-only `DEVICE_CAPACITY_PROFILE` bound to the Run contract, graph baseline, method lock, observation evidence, and prior profile digest. It contains explicit units and observation times for:

- logical CPU count and safely usable CPU concurrency;
- total and currently available RAM;
- GPU identity, applicability, available GPU count, and VRAM when applicable;
- available working disk, measured or conservatively declared IO throughput, and evidence space reserve;
- network and external-service availability, rate, and access restrictions;
- permitted process count and permitted/listened port constraints;
- maximal safe independent command/build/test concurrency;
- measured or conservative durations for commands, builds, focused tests, full regression, validation, hashing, and packaging;
- context-loading budget and evidence byte/file budget;
- observation source, freshness deadline, and uncertainty margin.

Values such as “high performance” or “resources sufficient” are invalid. A required dimension that is unknown, stale, unbound, or expressed without units fails closed. A genuinely non-applicable GPU/network dimension is allowed only with an explicit `NOT_APPLICABLE` reason and evidence.

GLK does not collect these measurements. It verifies caller-supplied observations through the existing provenance/profile boundary.

### CUMULATIVE_ENGINEERING_LOAD

The Supervisor appends a versioned `CUMULATIVE_ENGINEERING_LOAD` at plan freeze and after each important GO, outer Level, Graph boundary, or material estimate deviation. It binds:

- profile, graph, manifest, plan, and accepted-baseline versions;
- observed command durations and memory/disk peaks;
- current regression matrix size and duration;
- code/file/dependency/evidence/hash/index growth;
- context-recovery and independent-check cost;
- active resource reservations and external constraints;
- forecast uncertainty and safety margins;
- prior load digest and observation evidence.

Later load revisions must re-evaluate every undispatched CELL. Accumulated evidence normally makes later CELLs smaller or gives them a larger explicit verification budget unless current measurements prove the previous scale remains safe.

### CELL_WORK_ESTIMATE

Every CELL plan version contains a quantitative estimate of total engineering cost, not merely diff size. It binds:

- immutable GO outcome and acceptance references;
- implementation scope, inputs, dependencies, expected modifications, and generated artifacts;
- build and test matrix;
- independent Checker reproduction;
- affected regression surface;
- evidence, hashes, package/index updates, and cleanup;
- context loading and recovery;
- external tools, browser, network, ports, or services;
- rollback and retry allowance;
- coupling to the current accepted baseline;
- expected peak CPU, RAM, VRAM, disk, process, port, concurrency, duration, context, and evidence use;
- uncertainty and safety margins.

A small diff that triggers a full regression retains the full regression cost.

### CELL_CAPACITY_GATE

The mechanical gate consumes the exact current device profile, cumulative load, CELL plan/estimate, active reservations, graph/manifest versions, and observation evidence. Its closed result is:

- `PASS`;
- `SPLIT_REQUIRED`;
- `CAPACITY_BLOCKED`.

Only `PASS` permits dispatch to a Worker. Unknown capacity, expired observations, missing dimensions, unsafe resource overlap, or an estimate above a hard device bound is `CAPACITY_BLOCKED` unless a valid pre-dispatch split can fit. A large but splittable cost vector is `SPLIT_REQUIRED`.

The gate uses deterministic per-dimension comparisons and safety margins. Logical DAG independence and physical safety are separate: maximal-safe `ACTIVE_GO` is the largest DAG-eligible set whose resource claims do not exceed CPU, RAM, GPU/VRAM, disk/IO, process, port, external-service, or heavy-validation limits. Resource conflicts are typed constraints and must not be represented as fake dependency edges.

### Pre-dispatch splitting

`SPLIT_REQUIRED` creates a frozen `CELL_PLAN_AMENDMENT` before dispatch. Every successor CELL must be independently deliverable and D1-checkable, have explicit dependencies, and preserve the parent GO outcome and acceptance criteria. The amendment creates a new Required CELL set and manifest/plan version. It does not create a GO or a subagent and cannot reduce verification quality.

The gate is rerun for every successor. No successor dispatches without `PASS`.

### Execution scope excess

If actual work materially exceeds the frozen estimate, the Worker must not continue blindly, split the CELL, create another Worker, or create a subagent. It appends `CELL_SCOPE_EXCEEDED` with immutable checkpoint/evidence references and returns to the original Checker/planning authority for versioned re-planning. This is an execution-planning signal, not a D1 product defect.

### Post-dispatch split defects

Any split first required after dispatch records `POST_DISPATCH_CELL_SPLIT`. If one dispatched CELL needs three or more successors, it also records `CELL_OVERSIZE_SEVERE` and forces re-evaluation of the device profile, cumulative load, and every undispatched CELL. Splits into 6, 7, or 8 successors therefore always produce the severe signal and cannot be accepted as routine continuation.

Checker may reject a dispatch lacking a valid gate, but long-term capacity planning remains the Supervisor's responsibility and cannot be transferred to Checker rework.

### Capacity and progress interaction

A split or Required-set amendment updates the plan and manifest versions. Checker and Supervisor projections immediately recompute the current denominator. The historical `25/30` projection remains historical; the new version displays the new ordinal and denominator. The split alone adds no D1 acceptance.

## Authority and Artifact Classification

GLK 3.1.0 adds the following method-control objects:

| Object | Unique producer/controller | Classification | Forbidden authority |
| --- | --- | --- | --- |
| `WORKER_CHECKER_WAKE_BINDING` | Run Supervisor | append-only control | no D0-D3 verdict |
| `WAKE_ATTEMPT` | bound Worker | operational evidence | no acceptance/progress increment |
| `WAKE_ACK` | frozen Checker | operational evidence | no D1 verdict |
| `PENDING_WAKE` | bound Worker | append-only operational pending record | no technical verdict |
| `PATROL_OBSERVATION` | unique Run patrol | derived non-authoritative report | no repair, dispatch, or acceptance |
| `DEVICE_CAPACITY_PROFILE` | Run Supervisor | append-only control | no device collection or technical verdict |
| `CUMULATIVE_ENGINEERING_LOAD` | Run Supervisor | append-only control | no D0-D3 verdict |
| `CELL_WORK_ESTIMATE` | existing CELL planning authority under Supervisor control | append-only plan evidence | no dispatch decision |
| `CELL_CAPACITY_GATE` | Run Supervisor mechanical control | append-only gate | no product verdict |
| `CELL_PLAN_AMENDMENT` | Run Supervisor control | frozen amendment | no GO-outcome change |
| `CELL_SCOPE_EXCEEDED` | bound Worker | append-only execution signal | no self-split or product verdict |
| progress projections | validator-derived | non-authoritative | no receipt or state mutation |

`MONITOR_CONTROL` remains an append-only Supervisor control object but binds the unique patrol conversation/heartbeat rather than a waiting Supervisor task. Patrol consumption observations close pending wake records operationally without changing their history.

Schemas use closed role, event, result, and status enums. Formal technical registries continue to reserve D0-D3 authority for the six roles defined in GLK 3.0.0.

## Readiness and Preflight

`PREFLIGHT_PASS` additionally requires:

- exact Worker wake capability proof for every dispatchable Worker;
- frozen original Checker binding and host/thread identity;
- one unique patrol conversation and heartbeat descriptor;
- patrol model/effort/interval and forbidden-capability proof;
- Supervisor proof excluding positive-duration/looping wait behavior;
- closed subagent classifier and absence of prohibited capability grants;
- absence of Pin capability from every method role and the patrol;
- current `DEVICE_CAPACITY_PROFILE` with all required facts;
- current `CUMULATIVE_ENGINEERING_LOAD`;
- `CELL_CAPACITY_GATE=PASS` for every CELL about to dispatch;
- current progress denominator versions.

Readiness reports remain derived and non-authoritative. They reuse the existing method lock, package validator, and provenance boundary. Missing or self-reported-only facts fail closed.

## No-Side-Effect Simulation

Simulation uses a fake clock and local fake gateway. It must demonstrate without modifying the formal ledger:

- all four wake levels, exact two-minute boundaries, early-stop cleanup, wrong ACK rejection, and pending-wake patrol discovery;
- non-Worker wake rejection;
- Supervisor wait violation detection;
- one patrol and one heartbeat, legal pause suppression, subtask/subagent classification, and terminal closure order;
- Owner-authorized, Agent-authored, unknown-provenance, and Pin-then-Unpin histories without performing Pin/Unpin;
- Worker delivery versus D1 acceptance, duplicate/rework behavior, GO candidate versus D2, and amendment denominator recomputation;
- capacity PASS, `SPLIT_REQUIRED`, and `CAPACITY_BLOCKED`;
- early versus accumulated-load estimates for the same surface change;
- pre-dispatch split preserving one GO outcome;
- Worker scope-exceeded return and severe post-dispatch split handling;
- resource-aware maximal-safe activation distinct from DAG independence.

Simulation artifacts are `SIMULATION_ONLY`, live in the simulation root, and cannot become current formal evidence.

## Product Surface and Migration

Implementation updates only necessary product surfaces: version, SPEC, root/local Skill, focused references, schemas, templates, readiness, simulation, validators, tests, changelog, migration, manifest/report, repository hash manifest, and release package validation. The cross-method Pin rule is documented here only as the GLK conformance requirement; this version does not modify SLK, CLK, or other repositories.

The root `SKILL.md` and `glk/SKILL.md` remain byte-identical. Repository-distribution validation remains separate from Run-package validation.

Migration from GLK 3.0.0 preserves technical receipts, graph topology, causal history, exact CELL closures, and Owner Acceptance when otherwise current-valid. Existing `MONITOR_CONTROL` is historical-only for 3.1 patrol eligibility and must be reissued against the unique patrol conversation/heartbeat. Undispatched CELLs require new capacity profiles, load snapshots, work estimates, gates, and plan versions. Historical progress remains immutable but current projections are recomputed.

No migration creates conversations, heartbeats, tasks, sessions, agents, credentials, or external measurements.

## Acceptance Criteria

1. Level 1 direct Worker wake succeeds with a scoped GO/CELL ordinal message and stops escalation.
2. Level 1 failure followed by Level 2 same-Checker recovery succeeds without guessing or replacement.
3. Level 2 repairs wrong archive state and validates host identity.
4. Missing original Checker fails closed without creating a task or role.
5. Level 3 heartbeat is deterministic and unique, and ACK deletes it.
6. Three failed levels produce one `PENDING_WAKE` that the unique patrol can discover and consume.
7. Matching ACK or verified processing evidence immediately stops all later levels.
