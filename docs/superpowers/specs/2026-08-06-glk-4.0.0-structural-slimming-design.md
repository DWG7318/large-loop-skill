# GLK 4.0.0 Structural Slimming Design

## Status

- Status: repository-local single-kernel and surface-isolation phase complete;
  cross-method shared-control, validator decomposition, release-identity generation,
  and final 4.0 release remain deliberately open.
- Design date: 2026-08-06.
- Target version: 4.0.0.
- Base: released GLK 3.1.0 commit `2cbbd20167376e4ce57cd0e3a201e5fdb323c43f`.
- Scope: structural slimming without weakening GO-DAG semantics, technical authority, evidence lineage, or fail-closed validation.
- Release rule: GLK 3.1.0 remains immutable; GLK 4.0.0 is a new breaking release and never overwrites an older tag or Release.

This design replaces multiple executable truth sources with one graph kernel, moves cross-loop controls behind one shared contract, and leaves actual Agent Runtime operations to LCagent or another trusted execution environment.

The completed repository-local phase may enter `main` as unreleased maintenance but
does not claim a GLK 4.0 tag or Release. The released 3.1.0 tag remains immutable.

## Problem Statement

GLK 3.1.0 contains 126 tracked files and approximately 29,213 text lines. Its 46 Python files contain approximately 21,021 lines, including approximately 11,275 test lines. The distribution exposes 33 formal artifact types, 35 templates, and one 1,380-line schema with 63 definitions.

The size is not explained by graph topology alone. GLK 2.4 used 57 tracked files and approximately 5,600 lines. GLK 3.0 added an independent authority, package, provenance, and ten-layer validation system; GLK 3.1 then added cross-loop wake, patrol, Pin, progress, and capacity controls. A proposed model-policy change on the stopped 3.2 branch touched 103 files and added approximately 4,170 lines.

Four structural defects cause this fan-out:

1. `graph_model.py` and `run_state.py` both model graph topology, activation, closure, and state projection.
2. Standalone wake, progress, and capacity modules implement behavior that Layer 11 validates again in `run_validation.py`.
3. Rules common to SLK, CLK, and GLK are embedded as GLK-native artifacts and code.
4. Version, model, schema, template, repository, test, and hash identities are repeated across many files instead of deriving from one release identity.

The result is a method that describes itself as lightweight while carrying a parallel control kernel and a quasi-Runtime validation system.

## Design Goals

GLK 4.0.0 must:

- preserve GO-DAG identity and exactly six role types;
- preserve typed `WAITING_GO`, direct maximal-safe `ACTIVE_GO` activation, and the ban on fake dependency edges;
- preserve D2/admission/`GRAPH_EVENT` separation and D3 graph-seam verification;
- preserve confirmed-consumption causal tracing, minimal impact projection, and append-only amendment history;
- preserve fail-closed package, authority, provenance, isolation, and evidence validation;
- establish exactly one executable truth source for every graph rule;
- consume common Loop controls through one versioned binding instead of implementing them again;
- keep sessions, message transport, waits, heartbeats, liveness observation, model dispatch, and credential/runtime enforcement outside GLK;
- make ordinary policy or version changes narrow enough to review independently;
- keep historical 3.1 packages readable without treating them as current 4.0 evidence.

## Non-Goals

GLK 4.0.0 does not:

- simplify GLK into CLK or remove free branching and merging;
- weaken D0-D3 authority separation or evidence identity;
- convert graph dependencies into Chains, Stages, Barriers, or a `READY` queue;
- redesign SLK or CLK inside the GLK repository;
- create a fourth Loop method;
- create a second Agent Runtime beside LCagent;
- delete compatibility evidence before a replacement reader exists;
- rewrite all code at once;
- retain duplicate code merely to preserve internal module names.

## Alternatives Considered

### Trim documentation and tests only

Rejected. Documentation and tests contribute size, but the two graph engines and repeated operational logic would remain. This would improve appearances without reducing behavioral drift.

### Rewrite GLK from scratch

Rejected. GLK 3.0 and 3.1 contain hard-won authority, isolation, causal-recovery, and fail-closed regression rules. A rewrite would make it easy to lose a negative invariant that is not obvious from the happy path.

### Incremental single-kernel replacement

Selected. Characterize current accepted behavior, introduce one canonical graph kernel, route validators through it, remove the superseded truth source, then extract common controls. Every slice stays releasable or revertible and proves that a removed implementation has a tested replacement.

## Preserved GLK Core

The following remain native GLK responsibilities:

1. GO definition and frozen GO-DAG construction.
2. Mandatory D2 completion-precedence edges with actual-consumption bindings.
3. Typed waiting reasons and direct maximum-cardinality maximal-safe activation.
4. GO graph state and internal execution-phase separation.
5. Exact CELL-manifest to GO-candidate closure where required by D2.
6. Independent D2, Supervisor admission, and graph-event release.
7. D3 closure over required GO/D2 evidence and graph seams.
8. Confirmed causal trace, typed impact seeds, minimum impact projection, and graph amendment.
9. Immediate bounded Owner Acceptance and LCCoding security handoff.
10. Graph-specific validation and GLK method identity.

These rules form the acceptance boundary for slimming. A change that weakens one is not a slimming change and requires a separate Owner decision.

## Target Architecture

### One canonical graph kernel

`glk/scripts/graph_kernel.py` becomes the only executable owner of:

- canonical GO, edge, constraint, graph, manifest, and closure value objects;
- graph digest and topology recomputation;
- acyclicity and coverage checks;
- waiting-reason derivation;
- maximum-cardinality maximal-safe activation;
- D2/admission/graph-event state projection;
- causal trace validation and minimal impact projection;
- D3 graph-closure eligibility.

The kernel is deterministic and side-effect free. It receives immutable values and returns immutable projections or typed failures. It does not read files, invoke adapters, create tasks, send messages, or mutate Run ledgers.

`graph_model.py` and graph/closure logic in `run_state.py` are migration sources only. Once every accepted behavior is represented by kernel characterization tests and all production callers use the kernel, both old truth sources are removed. Compatibility import shims are temporary and cannot contain business logic.

### Thin validation orchestration

`run_validation.py` becomes an orchestrator rather than a second implementation. It:

1. receives one immutable package from the package loader;
2. validates serialization, index, authority, and provenance boundaries;
3. converts validated artifacts to kernel inputs;
4. calls the graph kernel once per projection;
5. validates exact artifact lineage against kernel results;
6. composes the derived non-authoritative report.

Graph topology, active-set, closure, and causal results must never be recomputed with separate local algorithms inside the validator.

Validation code is split by stable responsibility, not by release number:

- package and index integrity;
- authority and provenance;
- graph and closure lineage;
- Owner and handoff closure;
- compatibility readers.

The public CLI and report scope remain stable unless a breaking migration section explicitly changes them.

### Shared Loop control contract

Worker wake, Supervisor no-wait, unique patrol, subagent prohibition, Pin prohibition, layered progress, CELL capacity, and model selection are common Loop controls. They are not graph semantics.

The canonical shared contract is owned by the LCCoding control plane as one versioned asset, not as a fourth Loop method. SLK, CLK, and GLK bind the same contract version and digest. LCagent implements the real thread, wait, heartbeat, liveness, capability, and model-dispatch operations.

GLK retains only `LOOP_CONTROL_BINDING`, containing:

- contract identity, version, and digest;
- runtime adapter identity and attestation root;
- GLK role/scope mapping;
- graph-specific progress dimensions (`Required GO/D2`, `ACTIVE_GO`, and typed `WAITING_GO` reasons);
- graph-specific capacity reservations used by maximal-safe activation;
- exact current control-validation result reference.

GLK must not carry independent wake ladders, patrol schedulers, Pin logic, generic progress engines, or model-selection engines after the shared binding is current. A missing, stale, incompatible, or failed shared control result fails preflight closed.

The shared contract is pure method policy and validation. It does not create conversations, wait, wake, pin, schedule, select credentials, or execute models. Those remain runtime actions owned by LCagent.

### Formal artifact consolidation

Common operational records use one append-only shared control event envelope with typed event kinds and exact issuer rules. GLK does not need a separate top-level formal type and template for every wake attempt, ACK, progress trigger, and capacity observation.

GLK-native formal artifacts remain separate where authority or graph meaning differs, especially D0, D1, D2, Supervisor admission, `GRAPH_EVENT`, D3, Owner Acceptance, graph amendments, and method lock.

Consolidation must preserve:

- sole issuer;
- exact Run/GO/CELL/Round scope;
- candidate and digest binding where applicable;
- append-only lineage;
- evidence and provenance references;
- deterministic deduplication identity;
- fail-closed unknown event kinds.

### Release identity and generated distribution surface

One canonical release identity file owns method version, tag, schema version, validator version, Skill version, and canonical repository. Templates, manifest identity, validator constants, and hash inputs derive from it during release construction.

Generated outputs are verified but are not independently hand-edited. A version-only change must not require manual edits across all templates and tests.

Historical design and implementation plans remain in Git history or an archive area but are excluded from the formal runtime distribution and method-lock digest unless explicitly normative.

## Data Flow

```text
RUN_CONTRACT + GLK_METHOD_LOCK + LOOP_CONTROL_BINDING
    -> immutable package loader
    -> authority/provenance validation
    -> canonical graph-kernel input
    -> one graph/closure/causal projection
    -> artifact-lineage comparison
    -> shared-control result binding
    -> derived GLK validation report
    -> preflight admission
```

No stage may mutate formal artifacts. Reports and projections remain derived non-authoritative.

## Compatibility and Migration

GLK 3.1.0 remains immutable and valid for historical audit. On formal GLK 4.0.0 release:

- new formal 3.1 Runs are frozen;
- a 3.1 package is read through a compatibility reader and reported as historical 3.1;
- compatible GO topology, actual-consumption edges, candidate/evidence history, and amendments may be carried into a draft 4.0 migration package;
- 3.1 operational artifacts map to the shared control event model only through a derived migration report;
- no historical receipt or report becomes current 4.0 evidence without revalidation;
- old tags, Releases, hashes, and packages are never overwritten.

Compatibility code is isolated from the current kernel and current validator path. It runs in a release-only compatibility suite, not on every ordinary current-package validation.

## Failure Rules

GLK 4.0 fails closed when:

- more than one executable graph truth source remains current;
- validator-local topology or activation differs from the canonical kernel;
- a common control is implemented inside GLK after shared-contract cutover;
- runtime operations are performed by the method package;
- a shared control result is missing, stale, incompatible, or unbound;
- a version or model-policy change requires uncontrolled repository-wide manual edits;
- a historical compatibility path can issue current artifacts;
- slimming removes or bypasses a current negative invariant.

## Testing Strategy

Every implementation slice follows test-first replacement:

1. write a focused characterization or desired-interface test;
2. prove it fails for the expected missing boundary or duplicate behavior;
3. implement the smallest kernel or adapter change;
4. run focused tests;
5. run the affected validator and compatibility tests;
6. run the complete repository suite before a slice is accepted;
7. remove superseded code only after callers and tests prove replacement coverage.

Test ownership is consolidated:

- graph semantics are tested once against the canonical kernel;
- validator tests prove artifact-to-kernel binding and fail-closed seams;
- shared Loop controls are tested once in the shared contract package;
- GLK tests cover only graph-specific bindings to that contract;
- compatibility tests are separated from current-path tests.

## Quantitative Acceptance Gates

The final GLK 4.0 distribution must satisfy all of:

- one executable graph kernel;
- no production import of `graph_model.py` or `run_state.py` after their replacement;
- no GLK-native implementation of shared wake, patrol, Pin, generic progress, generic capacity, or model-selection behavior;
- total tracked text size between 12,000 and 16,000 lines unless an Owner-approved invariant requires more;
- Python production code below 8,000 lines;
- tests below 7,000 lines while retaining all negative-invariant coverage;
- `run_validation.py` below 900 lines or replaced by smaller responsibility modules;
- a method-version-only change touches no more than 12 tracked files;
- a model-policy-only change touches no more than 15 tracked files across the three Loop methods once the shared contract is adopted;
- repository validator, current Run validator, optimized-Python security subset, Windows/UTF-8-off checks, hash verification, and release-package integrity all pass.

Line budgets are guardrails, not permission to remove evidence. If an invariant prevents a budget, the design must document that exception before release rather than silently exceed it.

### Current repository-local result and exceptions

As of 2026-08-07, the current phase has one executable graph kernel, no current
`run_state.py`, no standalone progress executor, a legacy mutable graph model
isolated under compatibility-test support, release/repository/bootstrap
implementations under root `tools/`, and 7,956 Python lines under `glk/scripts`.

The 12,280-line recursive Python test surface is intentionally retained because it
contains distinct fail-closed authority, provenance, package, causal, operational,
and migration negatives. Moving support files does not count as test reduction.
Tracked text is 26,256 lines and `run_validation.py` remains 2,146 lines. These final
4.0 quantitative gates are not waived: they remain open for validator responsibility
decomposition and a generated runtime distribution. Native `cell_capacity.py` also
remains until the shared LCCoding Loop-control contract exists; deleting it earlier
would remove capability rather than remove duplication.

## Implementation Sequence

1. Establish size, import, truth-source, and version-fan-out regression gates.
2. Introduce the canonical graph-kernel interface with failing characterization tests.
3. Move graph topology, activation, closure, and causal behavior behind the kernel.
4. Route formal validation through the kernel and remove duplicate graph calculations.
5. Isolate 3.1 compatibility readers and remove superseded current implementations.
6. Establish the shared LCCoding Loop control contract and LCagent runtime boundary in a separately accepted cross-method slice.
7. Replace GLK-native common controls with one `LOOP_CONTROL_BINDING` and graph-specific adapter.
8. Centralize release identity, generate distribution metadata, and reduce version fan-out.
9. Run full migration, security, compatibility, packaging, and release acceptance.

Each numbered item closes with its own tests and commit. A later item cannot begin while an earlier item has an unverified current-path regression.

## First Construction Slice

The first implementation plan covers only items 1 through 3:

- add structural regression gates;
- introduce the canonical graph-kernel interface;
- migrate topology and maximal-safe activation into that kernel;
- keep public 3.1 behavior and artifacts unchanged;
- do not yet modify shared controls, migration, release identity, schema version, or remote state.

This slice proves the single-kernel direction with bounded risk before broader deletion begins.
